## 0.5 限流判定规则 v0.1(2026-08-13,C6 首批 + 收尾数据)

**C6 实测(2026-08-12 23:46-00:51)**:B站/抖音各 14 次探测(300s 间隔 ≈ 0.02 req/s),**全部成功零限流**(B站 avg 181ms max 874ms / 抖音 avg 344ms max 504ms),且探测期间真实捕获了 OFFLINE 状态(B站 4 次 / 抖音 3 次),证明低频轮询下状态解析稳定。**C6 收尾(08-13):两平台 14 条数据完整迁移至新目录,确认未触发限流信号,无"触发前请求数"可测——低频(0.02 req/s)× 1h 不足以触发,阈值仍以历史数据为准(B站首犯 8.3h / 累犯 25min)**。

| 信号 | 判定 | 动作 |
|------|------|------|
| HTTP 429 / 403 | RATE_LIMITED(平台显式限流) | 立即退避,指数递增 |
| `HTTPSConnectionPool` 连接超时 | **疑似限流**(连接级,非网络故障) | 连续 3 次 → 升 RATE_LIMITED |
| 慢响应 > 5× 基线(如 >1s) | 疑似限流/平台抖动 | 连续 5 次 → 升 RATE_LIMITED |
| 网络层异常(ProxyError/DNS) | NOT platform signal | 不升级,单独计数 |

**"连接超时→RATE_LIMITED"判定规则(建议,基于 C6 + Gate 0B 历史)**:
1. **单次连接超时**:保持 PARSE_ERROR/重试 1 次,不升级(网络抖动与限流无法单次区分)
2. **连续 3 次连接超时** → 升级 RATE_LIMITED,退避 30min(3 次已排除偶发;平台侧典型形态是拒连而非 429)
3. **慢响应 >60s 单次**:标记 SLOW 计入候选,连续 5 次 → 升 RATE_LIMITED
4. **恢复探测频率**:退避封顶 30s×2^n(30s/1min/2min/4min/8min),连续 1h 无信号恢复;**累犯(冷却 <48h)封顶提高到 30min**
5. **冷却规则**:限流后冷却 ≥2h 才可恢复探测(8/2 实测 ~2h 自动恢复)
6. **C6 未能实测"触发前请求数"**(1h 低频未触发)——该数值需 C1 QPS 阶梯或虎牙/斗鱼 C6 补测,当前以 B站 8.3h(首犯)/25min(累犯)为参考

**退避策略 v0.1**:触发 RATE_LIMITED → 退避 `30s × 2^n`(30s/1min/2min/4min/8min 封顶),连续 1h 无信号后恢复探测。**累犯(冷却 <48h 再触发)退避封顶提高到 30min**。
**冷却规则 v0.1**:限流后冷却 ≥2h 才可恢复探测(8/2 实测 ~2h 自动恢复)。

## 1. C1 持续 QPS 压测

### 1.1 设计

每平台用**单 IP 匿名**(与 Gate 0B 同环境,可对比),固定频率递增探测:

| 阶段 | 频率 | 持续 | 目的 |
|------|------|------|------|
| 基线 | 0.02 req/s(300s 间隔) | 30min | 确认无干扰 |
| 阶梯 1 | 0.5 req/s(2s 间隔) | 30min | 低频是否安全 |
| 阶梯 2 | 1 req/s | 30min | V1 目标频率 |
| 阶梯 3 | 2 req/s | 30min | 2 倍目标 |
| 阶梯 4 | 5 req/s | 30min | 5 倍目标(找上限) |

> **停止条件**:出现限流信号(慢响应 >60s 或连接拒连)即停,记录"该频率可持续时间"。

### 1.2 输出

- `sustained_qps` = 触发限流前最高可持续频率
- 触发前累计请求数(对比 B站 8.3h 基线)

## 3. C3 Batch Endpoint 调研(关键,决定容量模型)

| 平台 | 候选 batch 端点 | 单请求可查主播数 | 状态 |
|------|----------------|----------------|------|
| B站 | `getList`(推荐页) | 115 房间/请求(5 推荐 + 110 分区) | ✅ 已验证,**漏检率高** |
| B站 | `getRoomPlayInfo` / `getRoomInfoOld` | 不支持批量(逗号分隔 -400) | ✅ 已否定 |
| 抖音 | `webcast/feed` | **固定 6 房间/响应**(count 无效,分页无效,随机推荐) | ✅ 已验证,**不可用** |
| 虎牙 | `cache.php?m=LiveList&do=getLiveListByPage` | **120 房间/页 × 82 页** | ✅ 已验证,但**有漏检** |
| 斗鱼 | `directory/all`(页面内嵌 JSON) | **40 房间/页**(首页) | ✅ 已验证,但**有漏检** |

> **✅ C3 最终结论(2026-08-12,4 平台全部实测)**:
> 1. **无平台有"可靠全量"批量端点**:
>    - B站:首页 getList 115 房间漏检高;批量接口(-400)不存在
>    - 抖音:feed 固定 6 房间随机推荐,无法翻页 → 不可用作批量
>    - 虎牙:120/页 × 82 页但漏检(3 在播命中 2)
>    - 斗鱼:40/页但漏检(4 在播命中 1)
> 2. **批量端点只能当"ONLINE 单侧证据"**:命中列表 = ONLINE,未命中 ≠ OFFLINE(需单查确认)
> 3. **V1 容量模型**:B站/抖音 纯单房间探测;虎牙/斗鱼 可用"列表快照(热门命中)+ 单查补漏(冷门)"混合,但混合的净增益需漏检率统计确定
> 4. **漏检率统计(Gate 0C 待办)**:取 50 个在播房间样本,测各平台列表命中率,确定混合策略的实际收益

> **若 B站/虎牙/斗鱼有 batch endpoint,V1 容量模型完全不同**:
> - 无 batch:容量 = sustained_qps × 轮询间隔(单房间一个请求)
> - 有 batch:容量 = batch_size × sustained_qps × 轮询间隔(一个请求查 N 房间)
> - **但 batch 的"在播列表"语义只提供单侧证据(在 = ONLINE),OFFLINE 仍需单查或差异检测**

### 3.1 调研方法

用浏览器开发者工具抓**列表页/搜索页**的网络请求(参考抖音 web_rid 提取经验),找返回多房间状态的 API。脚本:`experiments/batch_probe/{platform}.py`。

## 6. C6 连接超时 vs RATE_LIMITED 因果实验

> **背景(2026-08-06 Gate 0B 实测)**:平台限流不是 429,而是慢响应(300s)+ 连接拒连(-1)。

### 6.1 要回答的问题

1. 连接超时连续 N 次(如 3 次)后,是否应升级为 `RATE_LIMITED`?
2. 慢响应(延迟 > 60s)是否也算限流信号?
3. 各平台恢复时间是否随累犯延长?自动退避参数(停 2h / 4h / 24h)怎么定?

### 6.2 实验方法

单 IP 匿名,固定频率轮询,记录"首犯时间 / 累犯时间 / 恢复时间"曲线:

```
时间轴:
  T0     持续低频轮询(0.02 req/s)
  T1     首次出现慢响应 / 拒连(记录:触发前累计请求数)
  T2     停止,测恢复(每 10min 探测 1 次,记录恢复时间)
  T3     恢复后立即再跑(测累犯:是否更快触发)
  T4     再次停止恢复,测"二次累犯"恢复时间
```

### 6.3 判定规则建议(草案,待实测确认)

| 信号 | 当前分类 | 建议 |
|------|---------|------|
| 连接超时 1 次 | PARSE_ERROR | 保持,重试 1 次 |
| 连接超时连续 3 次 | PARSE_ERROR | **升级 RATE_LIMITED**,退避 30min |
| 慢响应 >60s | OFFLINE(错误?) | **标记 SLOW + 计入限流候选**,退避 |
| 慢响应 >300s 持续 3 轮 | PARSE_ERROR | **升级 RATE_LIMITED**,退避 2h |
| RATE_LIMITED 恢复后再次触发 | RATE_LIMITED | 退避 ×2(2h → 4h → 8h → 24h 封顶) |

### 6.4 脚本

`experiments/throughput_test/c6_ratelimit_causality.py` — 自动跑上述时间轴,输出 JSON 报告。
