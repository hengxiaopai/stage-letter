# 功能设计与交付规范

更新：2026-08-24
适用范围：所有新增或修改的用户可见功能，包括小程序页面、组件、按钮、通知、搜索、订阅和后台操作。

## 核心规则

**先设计，后开发，最后验收。** 采用原型驱动、敏捷迭代的系统工程方法：先验证用户路径和业务约束，再实现最小可验收切片，持续根据真机和真实数据反馈迭代。

任何功能在修改 WXML/WXSS/JavaScript、API、数据库或 Worker 之前，必须先有一份同编号的功能设计稿。设计稿经确认后，前端必须按稿还原；若实现时发现业务约束，需要先更新设计稿和接口契约，不能默默偏离。

设计稿不是单纯效果图。它必须同时说明：用户在哪个场景使用、页面中控件放在哪里、点击后发生什么、后端写入或读取什么、失败时用户看见什么，以及怎样验证成功。

## 每项功能的交付包

建议文件位置：`docs/features/<功能编号>-<名称>.md`。

每个交付包必须包含以下六部分。

### 1. 业务目标与边界

- 要解决的用户问题与目标用户。
- 用户故事：`作为 <用户>，我希望 <操作>，从而 <收益>`。
- 非目标：这次明确不做的能力，防止页面被无关功能膨胀。
- 与现有 Gate、直播状态真相、通知额度及微信平台限制的关系。

### 2. UI 设计稿与页面布局

- 提供目标页面设计图；引用现有设计稿时写明文件名与版本。
- 说明页面入口、返回路径和底部 Tab 选中态。
- 按从上到下的区域描述布局：容器、卡片、标题、插画、按钮、间距和滚动边界。
- 每个可点击控件必须标明：文字/图标、所在区域、可见条件、禁用条件、点击热区与视觉状态。
- 必须设计六类状态：加载、正常、有数据为空、错误、无权限/额度不足、网络恢复后刷新。
- 小程序优先：安全区、TabBar 高度、单手可点击区域、长文本截断和低端机降级必须明确。

### 3. 交互与逻辑矩阵

每一个按钮、Tab、搜索框或开关都必须列入下表；没有后端动作也要明确写为“仅本地 UI 状态”。

| 控件与位置 | 用户动作 | 前端行为 | API / 参数 | 后端逻辑与数据 | 成功反馈 | 失败/边界反馈 |
| --- | --- | --- | --- | --- | --- | --- |
| 示例：首页订阅行右侧“管理提醒” | 点击 | 打开提醒设置页，传入订阅 ID | `GET/PATCH /subscriptions/{id}` | 读取/更新 `notify_enabled`；写审计记录 | 开关即时更新、Toast | 请求失败回滚开关并显示“保存失败，请重试” |

若功能会触发微信订阅消息、平台探测或第三方 API，还须写清：是否异步、多久刷新、`UNKNOWN/CONFIRMING/LIVE/OFFLINE` 的显示规则，以及不得把 provider 失败误显示为“未开播”。

### 4. 数据与接口契约

- 请求、响应和错误码示例；字段的来源、允许为空的原因和前端默认值。
- 数据库读写表、幂等键、事务边界及迁移需求。
- Worker、队列或后台任务的触发条件和重试边界。
- 隐私与敏感字段：AppSecret、令牌、openid、数据库密码永不进入设计图、日志、前端包或 Git。

### 5. 实现拆分与验收

- 前端文件、后端文件、迁移、测试文件的改动清单。
- 视觉验收：以设计稿为基准，在微信开发者工具和真机分别截图比对；说明允许差异。
- 功能验收：正常、空态、失败、权限拒绝、重复点击、重启恢复等测试用例。
- 真实外部动作必须单独标为“需用户授权”；不可用 mock 冒充真机或 provider 证据。

### 6. 发布记录

- 设计稿确认日期、实现分支、PR、测试结果、真机版本和已知限制。
- 若实现与已确认设计稿不同，记录原因和新的设计稿版本。

## 研发流程

1. 提出功能目标、用户场景和可衡量的成功指标。
2. 先制作低保真原型：页面信息架构、入口、返回路径、关键状态和按钮位置。此阶段优先验证“用户能否理解并完成任务”，不急于做视觉细节。
3. 确认后制作高保真设计稿与本规范的交互/逻辑矩阵，冻结本迭代的 UI、API 与数据契约。
4. 将功能拆成纵向用户故事切片，例如“用户关闭一名主播提醒，并在重启后仍保持关闭”。每个切片同时包含前端、API、持久化和验收，不按纯前端/纯后端造成不可用的半成品。
5. 按优先级实施最小可行切片；任何布局或按钮语义变更先回写设计稿。开发中保持主分支可运行、改动可回退。
6. 每个切片完成自动化测试、开发者工具验证与必要的真机验证，并记录实际反馈、缺陷和下一迭代决策。
7. 达成视觉与功能验收后，才暂存、提交、创建 PR 与合并；随后评审指标和反馈，决定继续迭代、扩大范围或停止。

## 原型与迭代节奏

- **原型评审**：先评审业务路径、信息层级、关键操作位置与异常状态；通过后才进入高保真还原。
- **一个迭代只解决一个主目标**：例如“提醒开关可控”或“站内消息可读”，不在同一迭代夹带无关视觉重构。
- **验收以用户故事为单位**：每条故事都要有可观察的完成条件、失败边界与真实/模拟证据。
- **每日同步风险**：第三方平台限制、微信审核、真实数据不稳定、视觉差异和数据库迁移风险应尽早记录，不延后到合并时才发现。
- **迭代回顾**：完成后记录实际数据、未达成原因与下一步，不把“代码存在”当作“用户价值已经交付”。

## 当前项目的设计基线

- 首页视觉与空态参考 [UI-DESIGN.md](UI-DESIGN.md) 及已提供的 01–09 页面设计图。
- 首页优先回答“谁正在直播”和“我订阅了谁”；发现、消息、我的各自承担独立任务，不能只因视觉一致而混合职责。
- 直播状态是业务真相：`LIVE`、`CONFIRMING/CHECKING`、`OFFLINE`、`UNKNOWN/DEGRADED` 必须有不同文案和行为。
- 任意主按钮都必须有明确去向或动作；不可出现点击无反应的装饰性 CTA。
