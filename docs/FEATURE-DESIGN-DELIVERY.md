# 功能设计与交付规范

更新：2026-08-25  
适用范围：所有新增或修改的用户可见功能，包括小程序页面、组件、按钮、通知、搜索、订阅、主播详情和后台操作。

## 核心规则

**先设计，后开发，最后验收。** 采用原型驱动、契约冻结、纵向切片的工程方法：先验证用户路径和业务约束，再实现最小可验收切片，最后通过自动化、开发者工具和真机证据验收。

任何功能在修改 WXML/WXSS/JavaScript、API、数据库或 Worker 之前，必须先有同编号的功能设计包。实现时若发现业务约束，需要先更新设计包和接口契约，不能让代码默默偏离。

设计稿不是单纯效果图。它必须同时说明：用户在哪个场景使用、页面中控件放在哪里、点击后发生什么、后端读取/写入什么、失败时用户看见什么、字段来自哪里，以及怎样验证成功。

## 每项功能的交付包

建议文件位置：`docs/features/<功能编号>-<名称>.md`。

每个交付包至少包含以下七部分。

### 1. 业务目标与边界

- 要解决的用户问题与目标用户。
- 用户故事：`作为 <用户>，我希望 <操作>，从而 <收益>`。
- 非目标：本迭代明确不做的能力。
- 与现有 Gate、直播状态真相、微信 grant、第三方 provider 限制的关系。

### 2. UI 信息架构与视觉稿

- 页面入口、返回路径和底部 Tab 选中态。
- 从上到下描述区域、卡片、标题、按钮、间距和滚动边界。
- 每个可点击控件写明：文案/图标、可见条件、禁用条件、点击热区与状态。
- 必须覆盖 loading、normal、empty、error、权限/额度不足、网络恢复后刷新等状态。
- 小程序优先考虑安全区、TabBar、单手点击、长文本截断和低端机降级。
- AI 生成效果图只作为探索；未写入 Figma Master 或设计契约前不视为正式实现基线。

### 3. 状态与字段来源

所有用户可见状态必须从统一 UI Contract 映射，不允许页面自己从 provider/DB 原始字段猜测。

当前直播 UI 状态：

```text
LIVE       → 正在直播
OFFLINE    → 未开播
CHECKING   → 正在确认
UNKNOWN    → 状态待确认
ERROR      → 暂时无法获取
```

Backend 的 `DEGRADED` 可映射 UI `ERROR`；`SUSPECT_*`、provider error、rate-limit 等工程状态不得直接展示。

每个新字段必须标注：

- `NOW`：已有稳定数据来源。
- `DERIVED`：由 StageLetter 自身数据计算。
- `OPTIONAL`：provider/adapter 明确支持且数据质量达标时才出现。
- `FUTURE`：当前不实现，不得用 mock/硬编码伪装完成。

需要同时写出来源：表/领域对象/API 字段/计算公式/允许为空原因。

### 4. 交互与逻辑矩阵

每一个按钮、Tab、搜索框或开关都必须列入交互矩阵；没有后端动作也要明确写“仅本地 UI 状态”。

| 控件 | 用户动作 | 前端行为 | API | 后端数据 | 成功反馈 | 失败反馈 |
| --- | --- | --- | --- | --- | --- | --- |
| 示例：主播详情提醒开关 | 切换 | 乐观更新或等待响应 | `PATCH /subscriptions/{id}/notification-preference` | NotificationPreference | 状态持久化 | 回滚开关并提示保存失败 |

若功能触发微信订阅消息、平台探测或第三方 API，还必须写清：异步/同步、刷新窗口、冷却、状态收敛和 provider 失败的 UI 语义。

### 5. 数据与接口契约

- 请求、响应和错误码示例。
- 字段来源、nullable 原因和前端默认行为。
- 数据库读写表、事务边界、幂等键和迁移需求。
- Worker/队列触发条件、重试和 lease/容量边界。
- 隐私与敏感字段：AppSecret、token、openid、数据库密码不得进入设计图、日志、前端包或 Git。
- legacy 与 formal 两条消费路径并存时，必须提供字段 parity 矩阵；不能让两个路径产生不同 UI 语义。

### 6. 实现拆分与验收

- 前端、API、Domain、DB、migration、测试的改动清单。
- 一个分支只解决一个主目标，优先纵向切片。
- 视觉验收：开发者工具 + 真机逐屏截图对照。
- 功能验收：正常、空态、失败、权限拒绝、重复点击、重启恢复。
- 真实外部动作必须单独标注“需用户授权/真实 provider”；不可用 mock 冒充真机证据。

### 7. 发布记录

- 设计确认日期。
- 实现分支。
- PR / merge SHA。
- 测试结果。
- 真机版本。
- 已知限制和下一迭代。

## 研发流程

1. 明确主目标、用户故事和成功指标。
2. 做低保真信息架构与状态图。
3. 做高保真视觉和交互矩阵。
4. 冻结 UI / API / Data Contract。
5. 创建单目标分支并实现纵向切片。
6. 跑自动化、开发者工具、必要的真机/真实 provider 验收。
7. 回写设计包、测试证据和已知限制。
8. 合并到 `main` 后，下一分支必须重新从最新 `main` 创建，避免长期漂移。

## 分支约定

- `main`：唯一合并基线，保持可运行。
- `codex/gate*`：历史 Gate/审计分支，不继续承载新 UI V2 功能。
- `codex/ui-v2-*`：当前 UI V2 与 Backend Contract 工作流。
- 当前下一分支：`codex/ui-v2-2-backend-contract`。
- 已合并分支可以保留作审计，但不得继续堆叠新提交；新工作从 `main` 派生。

## 当前项目设计基线

- 首页：谁正在直播 / 我订阅了谁。
- 发现：搜索昵称或粘贴直播/主页链接。
- 目标 TabBar：`首页 / 发现 / 动态 / 我的`；当前代码仍是“消息”，待动态模型同步。
- 主播详情：`概览 / 记录 / 数据 / 档案`。
- 记录：`列表 / 日历`。
- 数据：`统计 / 分析`。
- “开播日历 / 月度总结”属于主播详情，不独立占一级导航。
- `UNKNOWN != OFFLINE`；`probe` 时间不能用于精确开播规律分析。
- 首页订阅行 V2 采用整行进入详情，避免“进入详情 / 管理提醒”两个等权 CTA。
