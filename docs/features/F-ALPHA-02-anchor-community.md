# F-ALPHA-02 — 主播乐园（详情后的订阅关系空间）

状态：**方案设计中；未经原型评审不得进入前端或数据表实现**
优先级：V1 Alpha P1
入口：`首页订阅行 → 主播详情 → 进入主播乐园`

## 1. 为什么不是直接做“社区”

首页负责回答“谁在播、我是否要进直播间”；它不承担动态流或聊天。把部落信息直接堆到首页会挤掉直播状态、让通知产品失焦。

用户看到的名称暂定为 **主播乐园**：它是某一主播的订阅后空间，不是跨主播的公共广场。技术域名使用 `anchor_community`，以便后续支持部落、粉丝团等产品命名而不迁移数据模型。

## 2. MVP：可信信息空间（不开放 UGC）

| 详情页区域 | 用户动作 | 后端真相 | 页面结果 |
| --- | --- | --- | --- |
| `进入主播乐园` 卡片 | 点击 | 已订阅校验；主播/平台账号存在 | 进入该主播乐园首页 |
| 当前直播状态 | 查看 / 前往观看 | 复用 `PlatformAccount` + `LiveSession`，不另造状态 | LIVE 时显示直播卡；OFFLINE 显示最近场次 |
| 开播时间线 | 查看历史 | `LiveSession`、`LiveEvent` 只读聚合 | 最近开播/下播及提醒触发记录 |
| 提醒偏好 | 管理 | `UserSubscription.notify_enabled` 及后续提醒策略 | 在详情/乐园一致展示与编辑 |
| 官方活动 | 查看 | 仅管理员发布的 `anchor_announcements` | 空态为“暂未发布活动”，不可伪造粉丝内容 |

MVP 不提供发帖、评论、私信、群聊或用户头像墙；这些功能没有审核、举报、封禁和隐私设计时不能上线。

## 3. 后续 UGC（P2，必须独立立项）

只有满足以下条件，才开放“部落动态”：

1. 用户发布前完成昵称/头像及协议确认；不要求、不保存直播平台账号凭据。
2. `community_posts`、`community_comments`、`content_reports`、`moderation_actions` 具备审核状态、举报、下架、审计与频率限制。
3. 管理员有审核队列和封禁能力；敏感词、图片安全和未成年人策略完成。
4. 明确平台内容版权边界：不抓取或搬运主播直播内容；只存产品内原创文本和用户主动上传、经审核的素材。

## 4. 原型先行交付物

在编码前必须给出并评审以下 5 张 375px 小程序稿，全部使用冻结的品牌头、公告条、图标和 TabBar 规范：

1. 主播详情页：保留 `进入主播乐园` 卡片及点击热区。
2. 乐园 MVP 空态：未开播、无活动、但订阅关系存在。
3. 乐园直播态：确认 LIVE 的直播卡、入口、最近场次。
4. 乐园时间线态：三条真实历史场次与“暂无更多”状态。
5. P2 社区动态态：仅用于审核 UGC 方案，不得提前接入生产导航。

每张图旁必须写明：点击控件、API、权限条件、加载/失败/空态、数据来源与埋点。原型评审通过后才拆分前端、接口、迁移和测试任务。

## 5. MVP 接口草案（尚未实现）

```text
GET /api/v1/anchors/{anchor_id}/garden?openid=
  → 主播资料、当前可信状态、最近 5 场直播、活动公告、订阅权限

GET /api/v1/anchors/{anchor_id}/garden/timeline?openid=&cursor=
  → 游标分页的历史场次/系统事件

GET /api/v1/anchors/{anchor_id}/announcements?openid=
  → 已发布官方公告
```

- 所有接口先校验 `openid` 的订阅关系；未订阅返回可解释的 `403` 与“去订阅”入口。
- `LIVE` 只读取已确认状态；`UNKNOWN/DEGRADED` 显示最近可信检测时间，不能渲染为未开播。
- 不在此功能内扩大通知额度或绕过直播平台访问限制。

## 6. 验收标准

- 从首页订阅行和详情卡都能进入同一主播乐园，且 `anchor_id` 一致。
- 主播没有活动/历史时有真实空态；禁止为填充页面写假动态。
- 直播状态与首页、详情使用同一 `current_live_state`，三页不得出现互相矛盾的状态。
- UGC 未上线前，页面没有任何看似可发帖但无实际审核处理的按钮。
